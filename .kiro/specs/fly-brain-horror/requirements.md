# 需求文档：果蝇脑驱动的文字恐怖游戏

> 暂定名：**《缸中之蝇》(Fly in a Jar)**
> 参赛：Kiroween 2026，提交截止 2026-12-04 14:00（太平洋时间）
> 调研结果见 [research.md](./research.md)

## 简介

这是一款在浏览器里玩的文字恐怖游戏，界面模拟终端，支持中英双语。游戏里有两个"大脑"，分工如下：

- **果蝇脑（编故事）：** 在 FlyWire v783 真实连接组上运行 LIF 模型。每回合给果蝇脑施加刺激，用它的放电模式从预写的片段库里挑选并组合接下来发生的事：场景、怪物、异象、线索。果蝇脑不理解玩家，它的反应带有生物性的混沌，这就是故事的来源。
- **Jev（当裁判）：** 玩家输入自由文本行动，Jev 结合当前游戏状态判断该行动是否可行，返回带概率的类型化结果。Jev 不生成任何文字。

后端用 Python（FastAPI），前端是浏览器中的模拟终端，用 Docker 部署在一台 2 核 4 GB 的 VPS 上。

## 术语表

- **连接组（Connectome）：** FlyWire v783 发布的成年雌性果蝇全脑神经元连接数据，约 13.9 万个神经元。
- **LIF 模型：** 漏电整合放电（leaky integrate-and-fire）神经元模型。
- **刺激（Stimulus）：** 对一组指定神经元施加的输入，例如味觉、嗅觉、视觉感受神经元。
- **读出组（Readout Group）：** 一组被观察的神经元。它们的放电情况会被转换成故事选择。
- **故事片段库（Fragment Library）：** 预先写好的恐怖文本片段，每个片段带标签和中英两个版本，由 Gemini 撰写。
- **判定（Verdict）：** Jev 对玩家行动返回的结构化结果，包括"可行/不可行"及其概率。剧情里判定你的声音叫 JEV（一种嗜神经病毒的研究所代号），实现上始终是 Jev API，同名是有意的双关。
- **同化率（Synaptic Sync）：** 玩家被果蝇脑同化的程度，0% 起，坏事让它上升，到 100% 进入"被吞噬"结局。分三档：0–30% 人类视角、31–69% JEV 潜伏期（双重感官）、70–99% 本能接管（指令劫持生效）。它替代了传统的"理智值"，但方向相反（数值越高越糟）。
- **感官投喂（Sensory Feeding）：** 玩家用特定动作抬高某条神经通路的放电倾向，但真实连接组仍决定结果，并有疲劳递减。
- **指令劫持（Neuro-Hijack）：** 同化率高时，果蝇脑的放电可能篡改玩家本回合的行动。
- **大脑日志（Brain Log）：** 终端中显示的神经活动记录：本回合刺激了哪些神经元，哪些读出组放电了。
- **回合（Turn）：** 玩家输入一次行动，系统完成判定、模拟和叙事输出，算一个回合。

## 需求

### 需求 1：浏览器模拟终端

**用户故事：** 作为玩家，我想打开一个网页就能在类似终端的界面里玩，不用安装任何东西。

**验收标准：**
1. 当玩家打开游戏网址时，系统应显示一个模拟终端界面：深色背景、等宽字体、闪烁光标。
2. 当玩家输入一行文字并按回车时，系统应把该行发送给后端，并在终端中回显。
3. 当后端返回叙事文本时，系统应以逐字打出的效果显示文本。
4. 当后端正在处理某个回合时，系统应显示等待提示（例如"神经元正在放电……"），并锁定输入，直到该回合结束。
5. 系统不得向浏览器暴露真实的 shell 或 pty。终端只是界面，所有输入都按游戏指令处理。
6. 系统应支持 `help`、`look`、`status`、`restart`、`lang` 等基础指令。具体指令集在设计阶段确定。

### 需求 2：双语

**用户故事：** 作为玩家，我想用中文或英文玩，评委也能看懂。

**验收标准：**
1. 当游戏首次加载时，系统应让玩家选择语言（中文 / English），默认选中 English。
2. 当玩家输入 `lang zh` 或 `lang en` 时，系统应切换之后所有系统文本和叙事文本的语言，并保留当前游戏进度。
3. 所有系统提示、指令说明、大脑日志标签和结局文本都应有中英两个版本。
4. 玩家可以用任一语言输入行动。发给 Jev 的问题说明和游戏状态一律用英文，玩家的原始输入原样附在 state 中。（Jev 对中文行动文本的判定效果需要在设计阶段实测）

### 需求 3：果蝇脑模拟引擎

**用户故事：** 作为玩家，我想知道故事真的出自一个真实果蝇大脑的神经活动，而不是预设脚本或随机数。

**验收标准：**
1. 系统应加载 FlyWire v783 连接组数据，作为模拟的网络结构。
2. 系统应在该网络上运行 LIF 模拟，参数参考 Shiu et al. 2024（Nature）。
3. 当某个回合开始时，系统应根据当前游戏状态选择一组刺激神经元，并在设定的时长内施加刺激。
4. 当模拟结束时，系统应返回各读出组的放电统计，例如放电次数和首次放电时间。
5. 单个回合的模拟耗时应在 3 秒以内（目标值，设计阶段根据实测调整）。
6. 如果实时模拟达不到耗时目标，系统应支持预计算或缓存放电结果作为替代方案。
7. 系统应允许设置随机种子，使同一种子和同一串输入能复现同一局游戏，便于调试和录制 demo。
8. 原始连接组数据不得提交到 git 仓库。系统应提供一个预处理脚本，从 FlyWire 官方来源下载原始数据，并转换成紧凑的二进制格式（例如 NumPy `.npz`）。
9. 预处理后的数据文件应直接提交到 GitHub 仓库，单个文件不超过 50 MB（GitHub 在 50 MB 时开始警告，100 MB 时拒绝提交）。不使用 Git LFS，因为它的免费流量额度很小。
10. 如果预处理后的文件超过 50 MB，系统应改为把文件放到 GitHub Releases 附件，在构建 Docker 镜像时下载。
11. 仓库中重新分发的数据文件应附带 FlyWire 的许可声明和论文引用。

### 需求 4：放电模式 → 故事

**用户故事：** 作为玩家，我想每一局的故事都由果蝇脑的反应决定，每次玩都不一样。

**验收标准：**
1. 系统应定义从读出组放电结果到故事要素的映射。故事要素包括场景转换、怪物行为、异象类型、氛围强度和线索出现。
2. 系统应根据映射结果，从片段库中挑选并拼接片段，生成本回合的叙事文本。
3. 叙事文本只能来自片段库。系统运行时不得调用任何会生成文字的语言模型。
4. 系统应保持故事连贯：已出现的场景、物品和怪物要记录在游戏状态中，后续片段不能与之矛盾。
5. 当所有读出组都没有放电（"死寂"）时，系统应把它当作一种有意义的事件来叙述，例如寂静、停电、心跳声，而不是报错。

### 需求 5：故事片段库格式

**用户故事：** 作为作者，我想让 Gemini 按固定格式批量写片段，写完直接放进游戏就能用。

**验收标准：**
1. 片段库应为 JSON 或 YAML 文件。每个片段应包含：唯一 ID、类别、标签、触发条件、中文文本、英文文本。
2. 系统应提供一份片段格式说明和示例，可以直接交给 Gemini 当写作提示。
3. 系统启动时应校验片段库：缺字段、ID 重复、缺少某种语言、引用了不存在的标签都要报错，并指出出错的片段 ID。
4. 当某个故事要素在片段库里没有可用片段时，系统应回退到该类别的通用片段，不得崩溃。
5. 片段库至少应覆盖：每种故事要素、每个失败原因类别、"死寂"事件、开场和每个结局。

### 需求 6：Jev 判定玩家行为

**用户故事：** 作为玩家，我想自由输入任何行动，并由一个公正又冷漠的裁判决定这件事能不能做成。

**验收标准：**
1. 当玩家输入一个行动时，系统应把"当前游戏状态（英文）+ 玩家行动原文"作为 state 发给 Jev，并附带预先定义好的英文类型化问题。
2. 问题集应至少包括：
   - 该行动是否可行（Noul，返回是的概率）
   - 不可行的原因类别（Choice，例如：物理上不可能、缺少物品、目标不存在、违背场景规则、不是行动）
   - 该行动的危险程度（Score）
3. 系统应根据可行概率和配置的阈值，得出"成功 / 失败 / 勉强成功"等结果。阈值可配置。
4. 当行动被判为不可行时，系统应增加同化率，并从片段库中选取与原因类别对应的文本来叙述失败。增量可配置，可以按原因类别或危险程度区分。系统不得显示 Jev 的原始输出。
5. 当行动被判为可行时，系统应把行动结果写入游戏状态，并把行动类型作为下一次果蝇脑刺激的输入之一。这样果蝇脑才能"感知"玩家做了什么，形成闭环。
6. Jev 的 API key 只能从环境变量 `TYPESAFE_API_KEY` 读取，不得写进代码、日志或前端。
7. 当 Jev 请求失败或超时时，系统应在终端以游戏内的方式提示（例如"裁判沉默了"），允许玩家重试，不增加同化率，并且不得让游戏崩溃。
8. 系统应提供一个本地 mock 判定器，返回结构相同的结果，用于离线开发和测试。

### 需求 7：大脑日志

**用户故事：** 作为玩家和评委，我想看到果蝇脑每回合到底做了什么，相信故事真的来自神经活动。

**验收标准：**
1. 每回合叙事输出之后，系统应在终端中用醒目的样式（例如暗绿色）显示一段大脑日志。
2. 大脑日志应包括：本回合刺激的神经元类型和数量，各读出组的放电次数，以及放电结果对应到了哪个故事要素。
3. 涉及神经元类型时，大脑日志应使用 FlyWire 的真实细胞类型名称。
4. 当玩家输入 `brainlog off` / `brainlog on` 时，系统应隐藏或显示大脑日志。默认显示。
5. 大脑日志中可以显示 Jev 判定的可行概率，例如"裁判：可行 12%"，便于评委理解判定过程。

### 需求 8：游戏循环与状态

**用户故事：** 作为玩家，我想要一局有开头、有推进、有结局的完整体验。

**验收标准：**
1. 一个回合的处理顺序应为：接收行动 → 指令劫持判定 → Jev 判定 → 更新状态（含同化率变化）→ 果蝇脑模拟 → 生成叙事 → 返回前端。
2. 系统应为每个玩家会话维护独立的游戏状态，包括当前场景、物品、同化率、已触发事件、上一回合放电结果、刺激疲劳、回合数和语言。
3. 当同化率达到 100%，或触发其他结局条件时，系统应结束本局并显示结局。系统应实现 4 种结局：逃脱、被吞噬、成为神经元（隐藏）、静默的标本（第四结局）。
4. 一局的游玩时长目标是 25–40 回合（约 15–25 分钟），适合评委体验和录制 demo。
5. 当玩家输入 `restart` 时，系统应重置游戏状态并开始新的一局。

### 需求 11：强互动机制

**用户故事：** 作为玩家，我不想只是跑图捡道具，我想真的去"玩弄"那个果蝇大脑，并感受到它反过来侵蚀我。

**验收标准：**
1. **感官投喂：** 当玩家的行动匹配到配置中的投喂动作（如敲桌、含糖、频闪、转圈）时，系统应抬高对应神经通路的刺激放电倾向，但最终结果仍由真实连接组的放电决定，不得保证成功。
2. **疲劳：** 当玩家连续使用同一条通路的投喂时，系统应逐次削弱其效果；换用其他通路后重置。
3. **指令劫持：** 当同化率 ≥70% 时，系统应根据上一回合的读出结果和当前同化率，以一定概率把玩家本回合的行动替换为本能动作（如进食、惊跳、僵住），并在终端以醒目样式标明这是神经劫持。
4. **同化率分档文本：** 关键片段（开场、结局、异象、进入场景）应支持按同化率三档呈现不同措辞。非关键片段可只提供单档。
5. **机房终端：** 恢复供电后，当玩家在机房与终端交互时，系统应对 `status`、`kill -9 specimen_F`、`stimulate PAM` 等固定输入返回预设的剧情响应，其中 `stimulate PAM` 应驱散怪物但显著提高同化率。
6. **瓶中之蝇：** 当玩家持有装着果蝇的管子时，系统应让怪物不再攻击玩家（仅逼近），并在叙事中让管里的果蝇反映当前回合的果蝇脑状态。
7. 以上机制都不得破坏"每回合重新模拟、服务端无会话状态、同种子可复现"的架构约束。

### 需求 9：部署（VPS）

**用户故事：** 作为参赛者，我想让评委点开链接就能稳定地玩到。

**验收标准：**
1. 系统应打包成 Docker 镜像，部署在 2 核 4 GB 的 VPS 上。同一个 FastAPI 进程既提供前端静态页面，也提供游戏 API。
2. 系统应在服务启动时加载一次连接组数据并常驻内存，不得每回合重新加载。
3. 整个服务的常驻内存应在 1.5 GB 以内，给系统和 Docker 留出余量。
4. 每个回合应作为一次独立的 HTTP 请求处理。游戏状态应保存在浏览器端，每回合随请求一起发送，这样服务重启也不会丢失玩家进度。
5. 果蝇脑模拟是 CPU 密集型计算。当多个玩家同时提交回合时，系统应排队处理，同时运行的模拟不超过 CPU 核数。排队时，前端应显示等待提示。
6. 系统应通过 `luckall.de` 下的一个子域名（暂定 `fly.luckall.de`）提供 HTTPS 访问。反向代理使用 Caddy，自动申请和续期证书。
7. 服务进程崩溃或 VPS 重启后，系统应自动恢复运行（例如 Docker 的 `restart: unless-stopped`）。
8. 系统应能在本地用一条命令启动（例如 `docker compose up`），方便开发调试。
9. 当多个玩家同时游戏时，各会话的状态不得互相干扰。
10. 系统应限制请求频率，避免 Jev 费用失控和服务器过载。
11. 系统应在服务器日志中记录每回合的耗时（Jev、排队和模拟分开记录），不记录 API key。
12. 整个项目不得使用收费存储。数据放在 GitHub，运行在现有 VPS 上。

### 需求 10：比赛提交

**用户故事：** 作为参赛者，我想满足 Kiroween 2026 的提交要求。

> 规则核实记录见 [kiroween-rules.md](./kiroween-rules.md)（2026-11-05 对照 https://kiroween.devpost.com/rules 核实）。

**验收标准：**
1. 代码应放在公开的 GitHub 仓库中（不用 GitLab 或 Bitbucket），带开源许可证文件，并且许可证要能在仓库首页的 About 栏被识别出来。
2. 仓库根目录应包含 `/.kiro` 目录，展示 Kiro 的使用情况（specs、hooks 和 steering）。`/.kiro` 及其子目录都不得写进 `.gitignore`。
3. README 应说明玩法、架构、如何运行，并引用 FlyWire 数据来源及论文（Dorkenwald et al. 2024、Schlegel et al. 2024、Shiu et al. 2024），遵守数据许可。
4. 应准备一段少于 3 分钟的演示视频：拍到游戏在浏览器里实际运行，公开上传到 YouTube，不使用未获授权的第三方商标、音乐或其他素材。
5. 提交时应附一份英文的 Kiro 使用说明，讲清楚 spec 驱动开发、steering、hooks 等功能是怎么用的。
6. 提交材料（视频、文字介绍、测试说明）应为英文，或附英文翻译。
7. 应提供一个评委可以免费直接打开的游戏网址，并在评审期结束前保持可用。

## 范围外（本次不做）

- 用语言模型在运行时生成或改写叙事文本
- 账号系统、存档云同步、多人联机
- 在浏览器端运行果蝇脑模拟
- 防止玩家篡改浏览器端保存的游戏状态（这是原型，作弊不影响别人）
- 移动端专门适配（能显示即可）

## 待确认问题

1. **Jev 对中文行动的判定效果：** 问题和状态已定为英文。玩家用中文输入时，Jev 能否准确理解中文行动原文，需要实测。如果效果差，再考虑在游戏里提供常用行动的英文关键词。
2. **FlyWire 数据许可：** 有来源说是 CC-BY 4.0，也有说是 CC BY-NC 4.0。两种许可都允许在开源、非商用的比赛项目中重新分发并注明出处，但开工前要去 flywire.ai 确认。
